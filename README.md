# Event Brief Builder

비디자이너가 블록을 쌓듯 문구·이미지·혜택·버튼을 배치하고 의미를 지정하면,
이미지 생성 AI가 바로 읽을 수 있는 구조화 기획서(`.eventbrief`)를 만드는 도구입니다.

> 단일 기준 문서: `EVENT_BRIEF_BUILDER_WORK_PLAN.md`
> 이 도구는 디자인 툴이 아니라 **기획 의도 배치판**입니다. 최종 디자인은 별도 이미지 생성기가 담당합니다.

## 현재 진행 상황

- ✅ **Phase 0** — Vite + React + TypeScript(strict) 프로젝트 구성, lint/typecheck/test/build 스크립트, 3열 UI 셸
- ✅ **Phase 1** — 도메인 스키마(Project / BriefBlock / Asset / PublishingInfo), 블록 타입 카탈로그, 검증 규칙, AI용 designSummary 생성기, 샘플 fixture, Vitest 단위 테스트
- ✅ **Phase 2** — 기본 UI(팔레트·캔버스·속성 패널), 블록 생성/선택/삭제, 편집, 키보드 삭제 보호
- ✅ **Phase 3** — 캔버스 편집: 드래그 이동(그룹 단위), 코너 리사이즈, 복제, 다중 선택·그룹화/해제, Undo/Redo(제스처 병합)
- ✅ **Phase 4** — 이미지 자산: 파일 업로드·다중 업로드·드래그앤드롭·Ctrl+V 붙여넣기, 원본 파일명/투명 배경 보존, IndexedDB(Dexie) 자동저장 및 새로고침 복구
- ✅ **Phase 5** — 분리된 정보 영역: 디자인 입력 / 참고자료 / 퍼블리싱 3영역 시각 구분, 규칙 기반 AI 요약 미리보기(퍼블리싱 링크는 AI 요약에 미포함)
- ✅ **Phase 6** — `.eventbrief` 내보내기/불러오기: ZIP 패키징(manifest·brief·preview·assets/references), 내보내기 검증, preview.png(840px) 생성, 트랜잭션 방식 복원(블록·좌표·그룹·이미지 바이트 동일)
- ✅ **Phase 7 (Step 1)** — 제품 셸 도메인 기반: 멀티페이지 문서 스키마(`BriefDocument`)·페이지 순수 함수·v1→v2 마이그레이션·페이지별 참고 이미지 레이어·zoom 뷰 상태 분리, react-router-dom 최소 라우팅 셸(게이트/목록/편집기 진입)
- ✅ **Phase 7 (Step 2)** — 진입 게이트·공통 제품 셸 UI: 앱 헤더/브랜드, 업무 선택 게이트(기획서 생성·이미지 생성 2카드), `/briefs`·`/image-requests` 정직한 빈 상태(가짜 목록·가짜 건수 없음), 향후 요청 KPI 주입용 구조만 준비
- ✅ **Phase 7 (Step 3)** — 기획서 화면 상단 재구성: 게이트로 돌아가기 · `기획서 생성` 모드 표시 · 기획서 제목 입력란(단일 원본) · 파일 저장/불러오기 보조 메뉴 · `전달하기` Primary CTA(동작은 Step 7)
- ✅ **Phase 7 (Step 4)** — 멀티페이지: 캔버스 위 페이지 필름스트립(추가/복제/삭제/순서 변경/이름 변경), 페이지별 독립 blocks·그룹·캔버스 높이·참고 레이어, `.eventbrief` **v2 멀티페이지 저장·불러오기 round-trip**(페이지별 preview), v1 파일은 1페이지로 자동 마이그레이션
- ✅ **Phase 7 (Step 5)** — 참고 이미지 UI: `도움 도구` 참고 이미지 추가/교체/제거(출력 블록 아님), 보기 모드 캔버스만·나란히 보기(독립 스크롤·줌·원본 비율 맞춤)·오버레이(표시 on/off·투명도 0~100% 기본 35%·위치 맞춤). 참고 이미지는 AI 입력·preview 출력에서 제외
- ✅ **Phase 7 (Step 6)** — 편집 UX 단순화: 팔레트 정리(행사정보 세부 블록 숨김)+블록 검색, `퍼블리싱 정보` 별도 접이식 섹션, 우측 패널 축소(중요도·AI 전달·위치 힌트·삭제 버튼 제거), 캔버스 **인라인 텍스트 편집**·카드 ⋯ 메뉴(삭제/이미지 교체·제거). 기존 타입·`.eventbrief` 호환 유지
- ✅ **Phase 7 (Step 7)** — 이미지 생성 요청: **전달하기 → WorkRequest**(멀티페이지 `BriefDocument` 스냅샷) 생성·로컬 `RequestRepository`(재시작 후 복원), 이미지 생성 요청 목록·상태 필터(신규·확인·작업 중·완료)·상태 변경, 요청 상세에서 **작업본으로 편집기 열기**(제출 스냅샷 불변), 게이트/기획서 화면에 요청 상태 반영. 초안 목록·서버·실제 AI 생성은 제외
- ✅ **Phase 7 (Step 8)** — 전체 UI 리디자인(§14): **(8A) 전체 UI 리디자인** — 편집기와 제품 셸이 **하나의 디자인 토큰 팔레트**를 공유(앱 배경/표면/경계/텍스트, 기획서=인디고·이미지=바이올렛 강조, 반경 12/8px, Pretendard 계열 폰트). 공통 버튼·입력·카드 규격화, 선택은 **얇은 강조 링 + 은은한 글로우**, 상단 앱 바 64px, 정직한 빈 상태·`prefers-reduced-motion` 대응. **(8B) 840px 고정 캔버스 줌 시스템** — 논리 캔버스 폭은 **840px로 고정**하고, 화면 맞춤(축소만)·−/＋ 단계(25~200%)·100%로 표시 배율만 조정. 줌은 **뷰 상태이며 `BriefDocument`·`.eventbrief`에 저장되지 않음**(블록 좌표·출력 항상 1:1)
- ✅ **기획서 작성기 v1 완주** (1-A · 1-B · 1-C) — 문구 블록은 카드 장식 없이 **문구 영역 그 자체**(여백 4px, 종류·메뉴는 블록 밖 부유 막대), 팔레트는 `글 넣기 · 이미지 · 버튼·링크` 3개이며 새 블록은 즉시 입력 상태. 이미지 블록에는 **참고 캡처**를 한 장 붙일 수 있고(파일 선택·드롭·붙여넣기, 기본 320×210에 미리보기 약 148px), `image.referenceOnly`로 **최종 사용 이미지가 아님**이 데이터에 남습니다 — 필수 제품 자산·`verbatimImages`에서 제외되고 `.eventbrief`에서는 `references/`에 담깁니다. AI 요약은 `이미지 자리`(설명 + 참고 첨부 표시)를 별도 영역으로 보여 줍니다

#### 작성기 v1 인수검사 (기준 커밋 아래 "실제 작성 완주")

- 실제 브라우저(로컬 production build)에서 시험 기획서 **2페이지**를 처음부터 끝까지 작성: 제목 `아크웨이브 신상 발매 기념 이벤트`, 전체 컨셉, 1페이지(문구 2 + 이미지 자리 + 참고 캡처 + 이미지 링크 + 버튼·링크), 2페이지(문구 2 + 이미지 자리 + 버튼·링크)
- 확인된 것: 원문 보존, 블록 이동·크기 조절 후 재로드·페이지 전환 유지, 다른 기획서로 이동 후 복귀, 목록 검색, AI 요약(전체 컨셉·문구·강조·이미지 자리·참고 표시·버튼·URL 분리), `.eventbrief` 내보내기 → 새 환경 불러오기, `전달하기` 직전 최신 화면 반영, 콘솔 오류 0
- **아직 없는 것**: 실제 팀 간 전달·수신, 서버 저장·로그인, AI 이미지 생성, 최종 이미지 자산 선택, Excel 가져오기 — *작성기 v1 완료는 PLANMAKER 전체 완료가 아닙니다*
- ⛔ Phase 7 나머지(초안 목록 관리) · AI 이미지 생성은 아직 구현하지 않음

### 멀티페이지 도메인 (Phase 7 Step 1)

- `BriefDocument`(v2.0.0) = `project` + `pages[]` + `activePageId` + 공유 `assets[]`
- 각 페이지: 고정 **840px** 캔버스 + 블록 + 페이지 단위 **참고 이미지 레이어**(오버레이 투명도 기본 35%)
- 기존 단일 페이지 `EventBrief`(v1)·`.eventbrief` v1 파일은 `migrateToDocument`로 `pages[0]`에 무손실 마이그레이션
- 페이지 추가/복제(ID 재생성)/삭제/순서변경 순수 함수, 마지막 페이지 삭제 불가·활성 페이지 불변식 유지
- **zoom은 저장하지 않는 뷰 상태**(`canvasView.ts`) — `BriefDocument`/`.eventbrief`에 미포함
- 라우트: `/` · `/briefs` · `/briefs/new` · `/briefs/:id`(편집기) · `/image-requests` · `/image-requests/:id`

### 진입 게이트 · 제품 셸 UI (Phase 7 Step 2)

- 공통 셸 컴포넌트(`src/components/shell/`): `AppShellLayout` · `AppHeader` · `AppBrand` · `PageHeader` · `EmptyState` · `StatusBadge`
- `/` 게이트: 앱 헤더 + "어떤 작업을 시작할까요?" 인트로 + 진입 카드 2개(**기획서 생성** → `/briefs` 파랑, **이미지 생성** → `/image-requests` 보라). 카드 전체가 키보드 포커스 가능한 단일 링크
- **가짜 데이터 없음**: 요청 건수·상태를 지어내지 않음. 이미지 카드는 "요청 관리 연결 예정" 중립 안내만 표시하고, 향후 `RequestRepository` KPI(신규/작업 중/완료/전체)를 주입할 슬롯(`EntryCard.stats`)만 준비
- `/briefs`·`/image-requests`: 정직한 빈 상태. `/image-requests`의 신규/작업 중/완료 배지는 실제 값 0(지어낸 숫자 아님)
- 편집기(`/briefs/new`·`/briefs/:id`)는 기존 `AppShell`을 **수정 없이** 마운트
- 디자인 토큰은 `.shell` 클래스에 스코프 → 편집기 스타일과 분리. 색은 역할 구분에만 사용, 그라디언트/글로우 없음, `prefers-reduced-motion` 대응

### 멀티페이지 편집 · v2 파일 (Phase 7 Step 4)

- 캔버스 위 **페이지 필름스트립**(`PageTabs`): 페이지 추가 · 복제 · 삭제(마지막 1장 보호) · 왼쪽/오른쪽 이동 · 이름 변경(더블클릭 또는 메뉴)
- 블록 편집기는 단일 페이지 그대로 유지 — `BriefDocumentProvider`가 **활성 페이지를 `EventBrief`로 투영**해 편집시키고, 편집 결과를 문서에 되돌려 동기화(페이지 전환 시에만 재하이드레이트하여 페이지별 Undo 유지)
- 페이지별 독립 상태: blocks·블록 순서·그룹·캔버스 높이·참고 레이어 데이터(참고 이미지 **UI**는 Step 5)
- **자동저장이 문서(v2) 단위로 전환** — 새로고침 후 모든 페이지·블록 복원. 기존 v1 자동저장 스냅샷은 불러올 때 자동 마이그레이션
- `.eventbrief` **v2**: `document.json`(모든 페이지) + `previews/page-01.png…`(페이지별) + 공유 `assets/`·`references/`. 내보낸 뒤 다시 불러오면 페이지 순서·이름·activePageId·블록·그룹·캔버스 높이·참고 레이어가 동일하게 복원
- 기존 **v1 `.eventbrief`(단일 페이지)** 파일은 1페이지 문서로 자동 마이그레이션되어 그대로 열림

### 이미지 생성 요청 (Phase 7 Step 7)

- **요청 데이터**(`domain/workRequest.ts`): `WorkRequest` = 상태(`submitted`·`reviewed`·`in_progress`·`completed`) + **`submittedDoc`(불변 멀티페이지 스냅샷)** + `workingDoc?`(디자인팀 작업본) + 타임스탬프. 상태는 브리프와 분리
- **전달하기**(`TopToolbar`): 제목·내용 검증 후 현재 `BriefDocument`를 스냅샷으로 `WorkRequest`(신규) 생성. 편집을 계속해도 제출 스냅샷은 바뀌지 않음
- **로컬 저장소**(`services/requestStore.ts`, Dexie): 요청을 IndexedDB에 영속화 → **재시작 후 목록 복원**. 자동저장 프루닝은 요청이 참조하는 이미지도 보존
- **이미지 생성 목록**(`/image-requests`): 상태 요약 배지 + 필터(신규/확인/작업 중/완료) + 요청 카드(제목·전달일·상태·페이지 수·불러오기). 데이터 없으면 정직한 빈 상태
- **요청 상세**(`/image-requests/:id`): 같은 편집기 셸을 `이미지 생성` 모드로 열되 **작업본(`workingDoc`)에 바인딩**(제출 스냅샷 불변) · 상태 변경(신규/확인/작업 중/완료) · 이미지 생성 자리 표시(§13.4, 가짜 생성 버튼·진행률·결과 없음)
- **게이트/기획서 화면 반영**: 게이트 이미지 카드 신규·작업 중·완료 실수치 + 강조 문구, 기획서 생성 카드 전달·작업 중 요약, `/briefs`에 전달한 요청의 현재 상태 표시 — 상태 변경이 양쪽에 즉시 반영(§5.3)
- 제외(별도 후속 Step): 여러 기획서 초안 목록·draft 저장/불러오기·작성 중 수·서버 공유·실제 AI 이미지 생성

### 전체 UI 리디자인 (Phase 7 Step 8)

- **디자인 토큰 통일**(§14.2): 그동안 편집기(`:root --color-*`)와 제품 셸(`.shell`)이 서로 다른 팔레트를 쓰던 것을 **같은 값**으로 정렬 — 앱 배경 `#f5f6fa` · 표면 `#fff`/`#f8f9fc` · 경계 `#e4e7ec` · 텍스트 `#171923`/`#667085`, **기획서 강조 인디고 `#4f6ef7` · 이미지 강조 바이올렛 `#7557e8`**, 성공/경고/위험 상태색. 반경 12/8px, Pretendard·Noto Sans KR·Inter 시스템 폰트(네트워크 폰트 없음)
- **공통 컴포넌트 규격화**(§16): 버튼(`.btn`·`--primary`·`--danger`)·입력(`.field__input`·검색·제목)·카드를 토큰 기반으로 통일. 입력 포커스는 강조색 테두리 + 3px 소프트 링, 브라우저 기본 폼 느낌 축소(§14.7)
- **선택·상호작용**(§14.5): 블록 카드 선택은 **두꺼운 테두리 대신 얇은 강조 링 + 은은한 글로우**, 호버/전환 120~160ms, 상단 앱 바 64px, 이미지 생성 모드 배지는 바이올렛으로 구분
- **정직한 빈 상태·접근성**: 빈 상태 CTA 유지, 비활성 버튼 툴팁, `:focus-visible` 링, `prefers-reduced-motion` 시 애니메이션 제거
- **(8B) 캔버스 줌 시스템**(§14.7 "캔버스가 너무 작고 멀리 보이는 문제" 해소): 그동안 고정 0.6배로만 보이던 캔버스를 실제 줌으로 대체 — 캔버스 위 컨트롤(축소 −/현재 배율/확대 ＋·화면 맞춤·100%), 단계 25·50·75·100·125·150·200%, 키보드 `Ctrl/⌘ +·−·0`. 기본값은 **화면 너비 맞춤(축소만, 1:1 초과 확대 없음)**이며 뷰포트 리사이즈를 따라감. 사용자가 배율을 지정하면 수동 모드로 전환. 줌은 `canvasView.ts`의 **저장하지 않는 뷰 상태** — `BriefDocument`·`.eventbrief`·자동저장·preview에 미포함이고 블록 좌표는 언제나 1:1로 유지(줌은 표시 배율만 변경). 확대 시 캔버스 영역은 스크롤
- 8A는 순수 스타일·마크업 정렬, 8B는 뷰 전용 줌 배선 — 저장 데이터 구조·출력은 불변

## 두 표면과 배포

한 코드베이스가 **두 화면**을 낸다. `VITE_PLANMAKER_SURFACE` 하나로 갈린다 —
`studio`면 이미지 생성기, 그 밖의 값이거나 없으면 기획서 작성기다. 없을 때 작성기로
가는 것은 의도된 안전한 기본값이다: 환경변수를 빠뜨린 배포가 디자인팀 전용 화면을
다른 팀에게 열어 주는 것보다, 작성기가 열리는 편이 낫다.

| 표면 | 쓰는 사람 | Vercel 프로젝트 | `VITE_PLANMAKER_SURFACE` |
| --- | --- | --- | --- |
| 이미지 생성기 | 디자인팀 | `planmaker` (`planmaker-umber.vercel.app`) | `studio` |
| 기획서 작성기 | 상품팀 등 타 팀 | `planmaker-writer` | 없음 |

환경변수는 **환경마다 따로** 있다 (Production / Preview / Development). Preview에서
맞게 열렸다고 Production도 맞다는 뜻이 아니므로, 두 곳을 따로 확인한다.

## OpenAI 키를 어디에 두는가

두 갈래가 있고, **환경변수로 갈린다.** 브라우저는 서버에게 한 번 물어 어느 쪽인지
알고, 그에 맞는 것을 묻는다.

| 환경변수 | 갈래 | 팀원이 넣는 것 | 키가 있는 곳 |
| --- | --- | --- | --- |
| 없음 | `client-key` | 자기 OpenAI 키 | 그 사람 브라우저 |
| `OPENAI_API_KEY` + `PLANMAKER_ACCESS_CODE` | `server-key` | **접속 암구호** | Vercel 서버뿐 |

`server-key`로 두면 팀원에게 키를 건네지 않아도 된다. 브라우저는 그림과 지시만
보내고, 키를 붙이는 일은 서버 함수 안에서 끝난다 — 번들에도, 응답에도, 팀원
화면에도 키가 나오지 않는다. 암구호는 키가 아니라 이 사이트에서만 통하는 문자열이라
새어도 OpenAI 계정과 무관하고, 환경변수를 바꾸면 즉시 죽는다.

**둘 다 넣어야 한다.** `OPENAI_API_KEY`만 넣으면 서버가 모든 요청을 거절한다
(`server_not_configured`, 503). 로그인이 없는 공개 주소에서 키만 두면
`/api/generate-image`가 주소만 아는 사람이면 누구나 부를 수 있는 생성기가 되고,
그 사실은 요금이 청구되기 전까지 아무 데도 드러나지 않기 때문이다. 설정이 덜 끝난
배포는 눈에 띄게 고장 나는 편이 낫다.

규칙은 전부 `src/services/serverAccess.ts` 한 곳에 있다. 나중에 사내 시스템으로
옮길 때 바꾸는 것은 `resolveApiKey` 하나 — "키가 어디서 오는가"와 "누가 부를 수
있는가" — 이고, 브라우저 코드와 생성 흐름은 그대로 남는다.

## 도메인 계층 (`src/domain/`)

`.eventbrief` 파일의 `brief.json`이 유일한 원본 데이터입니다. 도메인 계층은 UI와 분리되어
있어 추후 GODO AI OS로 이식하기 쉽습니다.

| 파일 | 역할 |
| --- | --- |
| `blockTypes.ts` | 의미 중심 블록 타입 카탈로그 (색상·도형 추론 없음) |
| `briefSchema.ts` | Project / BriefBlock / Asset / DesignSummary / PublishingInfo 타입 |
| `factory.ts` | 기본값이 채워진 블록·기획서 생성 헬퍼 |
| `validation.ts` | 내보내기 전 오류/경고 검증 (WORK_PLAN §14) |
| `summaryBuilder.ts` | 규칙 기반 AI용 요약 + 퍼블리싱 정보 분리 (WORK_PLAN §15) |

### 핵심 설계 규칙

- **의미 중심**: 블록은 최종 컴포넌트가 아니라 의미 역할입니다.
- **위치는 소프트 힌트**: 좌표는 840px 기준으로 저장하되 AI에는 참고값으로만 전달합니다.
- **정보 분리**: 디자인 정보 / 참고 정보 / 퍼블리싱 정보를 명확히 구분하며,
  AI용 `designSummary`에는 퍼블리싱 링크(URL)가 절대 포함되지 않습니다.
